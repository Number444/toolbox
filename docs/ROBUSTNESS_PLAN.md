## P0 —— 丢数据级,优先修

### 1. 持久化文件原子写入

- **问题**:`JsonSettingsFile.Save` 用 `File.WriteAllText` 直接覆盖。写入中途断电、杀进程、文件占用,都会留下截断的 JSON;下次 `Load` 反序列化失败静默返回 default —— **表现为"设置/密码记录无缘无故全丢"**,且无任何痕迹可查。
- **暴露史**:密码生成器的记录文件、AppSettings、AudioflowSettings 全部走这条路。
- **方向**:`Save` 改为「写同目录 `.tmp` 临时文件 → `File.Move(overwrite)` 替换」;`Load` 失败时尝试回落读取 `.bak`(替换前把旧文件复制为 `.bak`)。改动只在 `JsonSettingsFile` 一个类内,调用方零改动。
- **验证**:单测覆盖——写入中模拟截断文件,Load 应回落 `.bak` 而非丢光。

### 2. crash.log 无界增长

- **问题**:`App.LogCrash` 用 `File.AppendAllText` 无限追加,无大小上限、无轮转。长期运行后日志文件可能膨胀到几十 MB。
- **方向**:追加前检查大小,超过阈值(如 2 MB)则截断保留后半部分,或滚动为 `crash.1.log`。同时考虑在设置页加一个「打开崩溃日志目录」入口,方便排查时取日志。
- **验证**:单测或直接构造大文件观察截断行为。

## P1 —— 崩溃/失效级,有过前科

### 3. SMTC 监听生命周期加固

- **问题**:`SMTCListener.StartAsync` 中 `GlobalSystemMediaTransportControlsSessionManager.RequestAsync()` 未见异常保护;网易云重启、系统休眠唤醒、媒体服务重启后,监听是否自愈无明确保障。失效表现是「悬浮窗再也不更新,必须重启软件」——不崩溃但功能死亡,最难排查。
- **暴露史**:此前修过 SMTC 读取浏览器信息的过滤问题、暂停切歌按钮不刷新的顽固问题,这条链路一直是故障高发区。
- **方向**:① `StartAsync` 加 try/catch + 失败重试(退避);② 增加看门狗逻辑:长时间收不到任何会话事件时重新 `RequestAsync`;③ 休眠唤醒(系统电源事件)后主动重建监听。不改事件分发架构,只加防护。
- **验证**:手动场景测试——网易云重启、系统休眠唤醒后悬浮窗应自行恢复。

### 4. EdgeGlowLayer 回归防护(测试清单,不改代码)

- **问题**:这是全项目改动次数最多、bug 最顽固的模块(透出、假亮边、遮挡闪烁、Hover 消失、崩溃,全出过)。每次修一个问题都可能复活旧问题——已经实际发生过两次。
- **方向**:不碰实现。写一份**人工回归清单**(放进 docs):遮挡透出、滚出视口、Hover 边界、界面切换、设置开关、悬浮窗/主窗口双场景、紧凑/大模式。以后每次动 EdgeGlowLayer 或其调用方,对照清单过一遍再交付。
- **验证**:清单本身即交付物。

### 5. QrCodeToolTests 既有失败

- **问题**:3 个测试失败并致测试主机崩溃,是改动前就存在的既有问题。后果:`dotnet test` 永远红,未来任何测试退化都会被这片红淹没,测试体系形同虚设。
- **方向**:定位 3 个失败用例的根因(疑似测试主机崩溃与二维码原生库/编码有关),能修则修;若是环境依赖问题,标记 Skip 并注释原因,让测试套件恢复绿色 baseline。
- **验证**:`dotnet test` 全绿。

## P2 —— 体验加固,有空再做

### 6. 设置损坏的用户可见性

- 现状:设置文件损坏 → 静默回落默认值,用户只觉得"设置没了"。P0-1 的原子写+备份落地后,可进一步在回落 `.bak` 仍失败时给一次轻提示(托盘气泡或下次启动横幅),告知"设置已重置,日志见 xxx"。

### 7. Core 纯逻辑单测补强

- `JsonSettingsFile`(配合 P0-1)、密码生成器种子算法、SMTC 会话过滤逻辑,都是不依赖 UI 的纯逻辑,补单测成本低,为后续重构提供安全网。

## 明确不做(本轮范围外)

- **插件运行时外置化**(dll 目录动态加载):动架构,当前无收益痛点。
- **渲染层重写/换渲染方案**:EdgeGlowLayer 虽然脆弱但已收敛,重写的风险远大于收益。
- **AOT/启动速度优化**:WPF 对 AOT 支持有限,收益不明确。
- **统一设置中心**:属于功能拓展,不属于鲁棒性。

## 建议执行顺序

P0-1 → P0-2 → P1-5(恢复测试绿 baseline)→ P1-3 → P1-4 → P2。

前四项加起来改动集中在 2-3 个文件,一天内可完成;P1-3 需要实测场景验证,耗时主要在测试。
