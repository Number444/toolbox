# 架构修复设计（2026-07-31）

对应 `docs/待解决-2026-07-31.md` 的 P1-9 ~ P1-12 四条架构问题。
目标：**让"插件式架构"的名义与实际重新一致**，不搬迁任何运行逻辑，悬浮窗行为代码零改动。
分两阶段：阶段 1 纯收敛（无行为变化），阶段 2 依赖倒挂消解（只改调用点）。

---

## 现状问题与目标形态

```
现状（名不副实）                    目标（名实相符）
─────────────────────────          ─────────────────────────
主程序 ──静态绑定──▶ 插件类型        主程序 ──接口/枚举──▶ Core ◀──实现── 插件
插件 ──借用──▶ 主程序命名空间        插件 ──使用──▶ Toolbox.Plugins.*（自有命名空间）
Core ──无──▶ DWM 基础设施            Core ──拥有──▶ Win32Native + DwmHelper
ToolRegistry 三策略（2/3 死代码）    ToolRegistry 单策略（策略 1 唯一路径）
```

## 阶段 1：纯收敛（预期零行为变化）

### 1.1 命名空间隔离（P1-9）

**只改 4 个冲突命名空间**，插件自有的 `Toolbox.Tools*`（工具类、悬浮窗、EdgeDock 等）不动——它们本就不冲突，改了徒增改动面。

| 插件文件（现有 namespace） | 改为 | 受影响的引用方 |
|---|---|---|
| `Helpers/EngineDownloader.cs`、`ImageFileHelper.cs`、`OcrHelper.cs`、`PaddleOcrWrapper.cs`（`Toolbox.Helpers`） | `Toolbox.Plugins.Helpers` | 主程序 `MainWindow.xaml.cs:9`（using 将只解析主程序自己的 Helpers）；插件内部互相引用（OcrTool→EngineDownloader 等）补 using |
| `Services/AudioflowSettings.cs`、`SoftwareUninstallService.cs`（`Toolbox.Services`） | `Toolbox.Plugins.Services` | 主程序 `App.xaml.cs:8`、`MainWindow.xaml.cs:11`、`ViewModels/MainViewModel.cs:6` 的 using 拆分为 `Toolbox.Services`（主程序 ToolRegistry）+ `Toolbox.Plugins.Services` |
| `Models/InstalledSoftware.cs`、`SortMode.cs`（`Toolbox.Models`） | `Toolbox.Plugins.Models` | 主程序 `Services/ToolRegistry.cs:2`、`ViewModels/MainViewModel.cs:5`——**注意这两个文件同时用 Core 的 `Toolbox.Models`（ITool 等）与插件类型**，需同时保留两个 using |
| `Controls/DockTriggerBar.xaml.cs`、`MusicContentControl.xaml.cs`（`Toolbox.Controls`） | `Toolbox.Plugins.Controls` | 主程序 `MainWindow.xaml.cs:73-74`（`FloatSizeMode`——阶段 2 会把它移走）；插件内部（MusicFloatWindow 等引用 MusicContentControl） |

**风险**：低。全部是编译器可兜底的机械改名（改错即编译错）。唯一注意点是 `ToolRegistry.cs`/`MainViewModel.cs` 的双 using 是否引入类型歧义——Core Models 与插件 Models 无同名类型（InstalledSoftware/SortMode 与 ITool/ToolCategory 等不同名），预期无歧义。

### 1.2 Win32 P/Invoke 收拢（P1-12）

**Core 新增 `Toolbox.Core.Win32Native` 静态类**（放 `Toolbox.Core/Helpers/` 下，命名随项目惯例），收拢全部重复声明：

|---|---|
| `DwmSetWindowAttribute` | `Helpers/Win32Helper.cs:25-30`、`Toolbox.Plugins/Helpers/DwmHelper.cs:61-62` |
| `DwmExtendFrameIntoClientArea` | `Win32Helper.cs:84-87`、`DwmHelper.cs:64-65` |
| `MARGINS` | `Win32Helper.cs:89-96`、`DwmHelper.cs:81-88` |
| `SetWindowPos` | `DwmHelper.cs:77-79`、`Toolbox.Plugins/Helpers/ClickThroughHelper.cs:109` |
| `GetCursorPos` | `Helpers/SystemTrayHelper.cs:68`、`MainWindow.xaml.cs:674-676` |
| 连带收拢 | `DwmHelper` 其余专用声明（`SetWindowCompositionAttribute`、`WINDOWCOMPOSITIONATTRIB`、`ACCENT_POLICY`、`DWMWINDOWATTRIBUTE` 等）一并入 `Win32Native`，DwmHelper 只留业务组合逻辑 |

主程序 `Win32Helper.cs`、插件 `DwmHelper.cs`、`ClickThroughHelper.cs`、`SystemTrayHelper.cs`、`MainWindow.xaml.cs` 的私有声明删除，改用 `Win32Native`。

**风险**：低-中。机械替换；需确保各调用点原有封装的附加逻辑（如 HRESULT 检查——Win32Helper:36-111 有 A13 修复的检查）合并进 Win32Native 或保留在调用侧，**不丢失既有防御**。

### 1.3 删除死代码（P1-11）

`Services/ToolRegistry.cs`：删除策略 2（plugins/ 目录 LoadFrom，:80-98）与策略 3（基目录加载，:100-117）及其链式回退逻辑，保留策略 1（Assembly.Load，:64-78），注释说明**策略 1 是唯一路径**（ProjectReference + 静态绑定保证 DLL 必在主输出目录且登记 deps.json；若策略 1 失败主程序自身已无法启动，降级路径无意义）。

**风险**：极低。删除前先确认策略 2/3 无被调用的引用（验证已确认）。

## 阶段 2：依赖倒挂消解（P1-10）

### 2.1 DWM 能力下沉 Core（改动最大但最机械）

`Toolbox.Plugins/Helpers/DwmHelper.cs`（静态类 + `BackdropType`、`CornerPreference` 枚举）**整体移入 Core**，命名空间 `Toolbox.Core.Helpers`（类名保持 `DwmHelper`，最小化调用点改动）。

- 前提：1.2 完成后 DwmHelper 的 P/Invoke 已全部在 Core 的 Win32Native——移动后 DwmHelper 只是 Core 内的薄组合层
- 依赖检查：DwmHelper 依赖 `System.Windows.Window`——Core 已引用 WPF（`EdgeGlowLayer`、`ThemedMenuWindow` 都是 WPF 类型），无新依赖
- 调用点：主程序 `MainWindow.xaml.cs:694,698` 改用 Core 的 DwmHelper；插件 `AcrylicMusicWindow.xaml.cs` 等使用点改 using（数量以实际 grep 为准，预计 4-6 处）

**效果**：主程序向 Core 要 DWM，不再指向插件。依赖倒挂的 DWM 部分消解。

### 2.2 FloatSizeMode 枚举移 Core

`MusicContentControl.xaml.cs:804` 的 `FloatSizeMode` 枚举（`Compact`/`Large`）移入 `Toolbox.Core.Models`，插件与主程序均从 Core 引用。1.1 中 `Toolbox.Controls` 改名后此枚举随迁，`Toolbox.Plugins.Controls` 不再含它。

### 2.3 悬浮窗控制器接口化（依赖倒挂的剩余部分）

**Core 新增接口**（`Toolbox.Core.Models` 或新建 `Toolbox.Core.Abstraction`，随文档治理决定）：

```csharp
public interface IMusicFloatController
{
    bool IsVisible { get; }
    event EventHandler<bool>? VisibilityChanged;
    void Show(FloatSizeMode sizeMode, bool blurEnabled);
    void Hide();
    void Close();
    void ToggleBlur(bool enabled);
    void SetSizeMode(FloatSizeMode mode);
    void ResetPosition();
}
```

**Core 新增静态宿主**（注册/获取点，避免主程序直接碰插件类型）：

```csharp
public static class MusicFloatControllerHost
{
    public static IMusicFloatController? Current { get; private set; }
    public static void Register(IMusicFloatController controller);  // 幂等，重复注册以最新为准
}
```

**接线**：`ToolRegistry`（主程序与插件唯一的桥）在策略 1 加载成功后执行 `MusicFloatControllerHost.Register(MusicFloatWindowManager.Instance)`。`MainWindow` 与 `MainViewModel` 中的 Manager 引用全部改为 `MusicFloatControllerHost.Current`（接口类型）。

**效果**：主程序对插件的编译期引用从"具体类型 + 静态调用"降为"经 Core 接口取实例"。插件 DLL 仍被主程序引用（工具类型经 ToolRegistry 静态使用——架构文档早已承认此耦合），但**悬浮窗控制面**与主程序解耦。

### 2.4 阶段 2 后主程序对插件的剩余引用（诚实声明，不消除）

- `ToolRegistry`：工具加载（ITool 反射）与 `InstalledSoftware`（卸载列表模型）——架构固有耦合，文档承认
- 插件 DLL 缺失时主程序仍无法启动——**接受**，这是"主程序框架 + 内置插件捆绑发布"的现实形态，ARCHITECTURE.md 如实描述

- ❌ 悬浮窗/音乐控件物理搬迁出插件层（踩坑最多的模块，收益小于风险）
- ❌ 插件 DLL 解耦为可选（捆绑发布是现实形态，文档承认）
- ❌ 工具类命名空间 `Toolbox.Tools*` 改名（不冲突，无收益）
